# AI Assistant Guardrails: Puihaha Membership System

**Read this fully before every task. These rules override convenience, speed, and cleverness.**

## Project
Membership management and transaction processing system for the Puihaha E-Learning Platform. Laravel + MySQL + Eloquent, Breeze (Blade) auth, Tailwind, GSAP. Built by two students in one day and graded against the rubric below. `PLAN.md` holds the phases; `DESIGN.md` holds the locked visual decisions.

## 1. Work protocol
1. **Before building anything,** state the rubric row it serves and give a plan of 10 lines or fewer. If it serves no row, say so and ask whether to skip it.
2. Build the smallest slice that satisfies the row. Don't pre-build for later phases.
3. **After building,** list each rubric check as PASS / PARTIAL / UNVERIFIED with evidence.
4. State exactly what you ran and what you didn't. Never claim code works, tests pass, or a migration succeeds unless you executed it and saw the output. If you can't run it, say "not run".
5. If a request conflicts with the rubric or these rules, say so and propose the compliant alternative instead of silently complying.

## 2. Scope: do NOT add
Roles or permissions beyond a single admin · member login/self-service portal · email/SMS · real payment SDKs · file uploads/avatars · REST API · queues/jobs/scheduled commands · multi-tenancy · localization · extra packages beyond Breeze, GSAP, and what Laravel ships. If something seems needed, ask first.

## 3. Domain invariants (enforce in the domain layer, never only in a view)
- A member belongs to **exactly one** category and **exactly one** level.
- Membership numbers are unique, generated by the system (`PUI-YYYY-000001`), never user-entered.
- Transaction reference numbers are unique and system-generated (`TXN-YYYYMMDD-0001`).
- Statuses: `Pending`, `Paid`, `Approved`, `Expired`, `Cancelled`.
- **Only Paid transactions may be Approved.** Enforced in model/service; any other attempt throws a domain exception shown to the user as an error message.
- Only Pending transactions may be Cancelled.
- A payment must belong to a valid transaction. Payment amount > 0 and ≤ remaining balance. Cancelled or already-Paid transactions accept no payments.
- Remaining balance = `amount_due` − sum of **succeeded** payments.
- `amount_due` is **copied from the level fee at creation** so later fee changes never rewrite history.
- Renewal: `starts_on` = current `expires_on` if still valid, otherwise today; `expires_on` = `starts_on` + level `validity_months`.
- Expired is **computed** from `expires_on` (scope or accessor). No cron.
- Members are **deactivated**, never hard-deleted. Categories and levels in use cannot be deleted (friendly error, never a raw SQL exception).

## 4. Code standards
- Strict MVC. **Controllers are thin;** each action does validate → call domain → redirect or view.
- **Every form uses a Form Request** (required fields, email format, unique email ignoring current record on update, unique membership number, valid foreign keys, payment amount rules).
- Business rules live in models or `app/Services`, never in Blade or controllers.
- `Route::resource` where it fits; **all routes named**. Use route model binding.
- Eloquent only: no raw SQL, no `DB::table` for ordinary queries. Eager-load (`with()`) to prevent N+1. Paginate lists.
- Wrap multi-step writes (payment + status update) in `DB::transaction()`.
- No duplicated blocks: extract Blade components or partials (form fields, status badge, flash message, table shell) when something repeats twice.
- Use `$request->validated()`, never `$request->all()`. Mass assignment via `$fillable`.
- Names are descriptive and consistent (`MembershipTransaction`, not `Txn`).
- Comment only the non-obvious (why, not what).

## 3b. Database rules
- Foreign keys with `restrictOnDelete()` on category and level. Indexes on foreign keys and search columns.
- Unique indexes: `members.membership_number`, `members.email`, `membership_transactions.reference_no`, `payments.gateway_reference`, category name, level name.
- **Schema is frozen after the Phase 1 gate.** Don't edit migrations casually. If a change is truly needed, say so and wait for both team members to agree, then rebuild with `migrate:fresh --seed`.
- Every migration must have a working `down()`.

## 4b. Design philosophies (apply to every task)

**Priority when they conflict:** rubric correctness > KISS > DRY > polish.

### DRY: Don't Repeat Yourself (serves *Code quality*)
- One source of truth per rule. Statuses, transaction types, and payment methods are PHP enums (e.g. `TransactionStatus`), never string literals scattered across controllers and Blade.
- Store and Update Form Requests share their rules (base class, trait, or a shared `rules()` method).
- Repeated markup becomes a Blade component the **second** time it appears: form field, status badge, flash message, table shell, empty state, page header.
- Repeated query logic becomes a model scope (`active()`, `search()`, `expired()`, `withBalance()`).
- Money, date, and reference-number formatting goes through one helper or accessor, never inline.
- Colors, fonts, and spacing come only from `DESIGN.md` tokens.
- Don't abstract before the second repetition. Three similar lines beat a premature abstraction (that's KISS).

### KISS: Keep It Simple (serves all rows, and the timebox)
- Choose the most boring Laravel-standard solution: resource controllers, Eloquent, Blade, Form Requests.
- The only abstractions budgeted are `TransactionService` and the `PaymentGateway` interface. No repositories, DTOs, event buses, CQRS, or custom base classes beyond what DRY above requires.
- One method does one thing. If describing it needs "and", split it. Use early returns; no more than two levels of nesting.
- If two solutions satisfy the same rubric row, pick the one with fewer files and fewer lines.
- Test: *can a classmate understand this in 30 seconds?* You'll have to explain it during the demo.

### WYSIWYG: What You See Is What You Get (serves *Interface* and *Transaction processing*)
Applied to this app: the screen, the database, and the printout must all agree.
- What the user is shown is what gets stored. Confirmation summaries (amount, level, dates, reference) render from the same data that is saved; the amount on the Pay button is the amount recorded.
- The printable receipt uses the same data and view as the on-screen transaction page. The print stylesheet may hide navigation and buttons but must never change values.
- Status badges, balances, and dashboard totals are always derived from the database, never hard-coded or stale. `data-count-to` equals the server-rendered number.
- No hidden state: when a rule blocks an action, the UI says why (e.g. Approve is disabled with "Requires full payment", and the server still enforces it).
- Forms keep the user's input after a validation failure (`old()`).
- Money-affecting or irreversible actions (record payment, cancel, deactivate) show a clear confirmation step before committing.

## 5. Payments: simulated gateway only
- Implement the `PaymentGateway` interface with `SimulatedGateway` as specified in `PLAN.md` section 6.
- **Never request, validate, log, or store card numbers, CVVs, or any real payment credentials.** The fake checkout has only a method selector and a "simulate outcome" selector.
- A repeated callback must not double-record a payment (unique `gateway_reference`).
- Don't suggest or integrate a real payment provider.

## 6. Frontend and GSAP
- Follow `DESIGN.md` strictly: **only its fonts, colors, and badge mappings.** No new hex values, no new fonts, no inline styles for color.
- One layout (`layouts/app.blade.php`) with navigation reaching every page. Every list has an empty state. Every form shows validation errors and success/error flash messages.
- Must be usable at 375px width. Tables get horizontal scroll or stacked layout on mobile.
- Status badges use the defined colors **plus** an icon or label, not color alone.
- GSAP is a progressive enhancement only:
  - Content visible without JS (`gsap.from`, never hide in CSS first).
  - Wrapped in `gsap.matchMedia()` for `prefers-reduced-motion`.
  - Never animate form inputs, validation errors, or content the user is actively reading or clicking.
  - Motion under 0.6 s (except count-up and the gateway timeline), driven by `data-*` attributes, with all logic in `resources/js/motion.js`.
  - Count-up must end exactly on the server-rendered value.
- Motion work doesn't start until the Phase 6 gate has passed.
